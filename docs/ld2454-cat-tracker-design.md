# LD2454 고양이 위치 추적 설계

## 1. 목적과 범위

`watchcat`의 카메라·Hailo 고양이 판정 흐름에 24 GHz mmWave 레이더
`HLK-LD2454`를 추가한다. 레이더는 움직이는 대상의 2D 위치와 속도를
지속적으로 보고하고, 카메라는 그 이벤트를 **고양이인지 확인하는 수단**으로
유지한다.

이 설계의 1차 목표는 다음과 같다.

- 고양이가 주로 다니는 방 또는 통로에서 움직임의 위치·방향·최근 궤적을
  실시간으로 볼 수 있다.
- 밥그릇, 화장실, 휴식 장소처럼 의미 있는 구역의 방문 이벤트를 남긴다.
- 관심 구역의 새 움직임을 카메라 촬영 요청으로 연결할 수 있다.
- 사람이 함께 있거나 레이더 ID가 바뀌어도, 레이더 결과를 고양이 신원으로
  단정하지 않는다.

다음은 1차 범위 밖이다.

- 레이더 하나만으로 개체의 종 또는 고양이 이름을 식별하는 기능
- 정지한 고양이의 지속적인 재실 감지 보장
- 레이더 좌표만으로 방 전체의 절대 좌표를 자동 보정하는 기능
- 영상 프레임을 계속 전송하는 기능

LD2454 제조사 안내 기준으로 이 모듈은 최대 8 m, 수평 약 ±60°, 수직 약
±30°, 최대 3개 움직이는 목표, 약 10 Hz 데이터 갱신을 제공한다.
[제조사 제품 안내](https://www.hlktech.com/NewsInfo-440.html)를 기준으로 하되,
실제 구현 전에는 구매한 모듈의 펌웨어 버전과 동봉된 공식 UART 매뉴얼을
확인한다. 이 문서는 특정 프레임 바이트를 가정하지 않는다.

## 2. 기존 watchcat과의 관계

기존의 사진 촬영과 Hailo 판정 경로는 보존한다. 레이더는 카메라의 전원을
깨우거나 촬영을 요청할 근거를 제공할 뿐, Hailo 결과를 변경하지 않는다.

```text
LD2454 ─UART─> 레이더 노드(ESP32) ─Wi-Fi HTTP─> Pi watchcat gateway
                                              │
                                              ├─> 웹 UI: 실시간 평면도·구역·이력
                                              ├─> 캣모니터 TFT: 요약 상태
                                              └─> 관심 구역 이벤트 시 capture 명령

캣센서 ──────────────── 기존 JPEG 업로드 ───> Pi gateway ─> Hailo cat 판정
```

역할은 명확히 분리한다.

| 구성요소 | 책임 | 책임 밖의 일 |
|---|---|---|
| LD2454 | 움직이는 목표의 원시 측정 | 고양이/사람 식별 |
| 레이더 노드 | UART 복호화, 프레임 검증, 짧은 추적 보정, 전송 재시도 | 카메라 프레임 보관·Hailo 호출 |
| Pi gateway | 이벤트 수신·보관, 구역 판정, 웹 상태 제공, 촬영 요청 조율 | 레이더 UART 처리 |
| Hailo/camera | 고양이 여부를 이미지로 검증 | 연속 위치 추정 |
| TFT | 최신 상태·관심 구역·오류를 간단히 표시 | 평면도 상세 편집 |

기존 `gateway/server.js`의 이미지 업로드, 명령 리스, Hailo 큐는 변경하지
않는다. 레이더 API와 상태는 별도 모듈 또는 별도 라우트로 추가하며, 이미지
상태와 레이더 상태를 같은 파일 전역 변수에 섞지 않는다.

## 3. 하드웨어 설치

### 3.1 권장 배치: 낮은 벽면 설치

첫 설치는 레이더 안테나 중심을 바닥에서 **25–40 cm** 높이에 둔 벽면 설치를
권장한다. 이는 고양이 몸통의 이동을 보기 쉽고, 센서의 좌표 평면을 바닥
동선으로 바로 해석할 수 있기 때문이다.

```text
위에서 본 방

  벽
  [LD2454] ────── 센서 정면(+Y) ──────> 방 안쪽
      │      \                    /
      │       \  관측 영역        /       X: 좌/우
      │        \                /        Y: 센서 앞 거리
      └─────────\──────────────/────────> +Y
```

- 고양이가 자주 지나는 통로 또는 관찰할 구역을 정면에 둔다.
- 센서의 바로 앞 0.5–1 m에는 선풍기, 흔들리는 커튼, 관엽식물, 회전 의자처럼
  지속적으로 움직일 물체를 두지 않는다.
- 센서 정면을 유리·금속 문, 큰 수납장, 사람의 장시간 동선에 직접 향하지
  않도록 한다.
- 양면테이프나 임시 브래킷으로 며칠 측정한 뒤에만 나사 또는 강한 접착제로
  고정한다. 설치 위치와 정면 방향은 설정 파일에 기록한다.
- 안테나 앞을 금속으로 가리지 않는다. 케이스가 필요하면 얇은 ABS, PLA,
  아크릴 같은 비금속 재질을 사용한다.

### 3.2 천장 설치의 위치

천장 설치는 넓은 바닥을 하나의 레이더로 덮는 데 유리하지만, 센서 좌표를
바닥 평면 좌표로 변환해야 하고 가구에 의한 가림도 커진다. 따라서 1차에는
사용하지 않는다. 벽면 설계가 안정된 뒤, 복수 레이더 또는 천장 설치를
별도 실험으로 평가한다.

### 3.3 전원·배선

LD2454는 5 V 전원과 TTL UART를 사용한다. 레이더 노드는 ESP32-S3 계열을
권장하며, 현재 카메라 노드와는 물리적으로 분리된 별도 보드를 사용한다.
카메라 보드의 핀·PSRAM·프레임 버퍼 위험을 레이더가 공유하지 않게 하기
위함이다.

| LD2454 | 레이더 노드 | 주의 |
|---|---|---|
| 핀 1: 5V | 안정된 5 V | 부팅·Wi-Fi 송신 중 전압 강하가 없는 전원 사용 |
| 핀 2: G (GND) | GND | 반드시 공통 접지 |
| 핀 3: T (UART_TX) | ESP32 RX (별도 HardwareSerial) | 센서가 보낸 데이터 수신 |
| 핀 4: R (UART_RX) | ESP32 TX | 설정 명령이 필요할 때만 연결; 초기 관측만이면 미연결 가능 |

- 모듈의 핀 표기는 사진의 안테나 면을 위로 놓고 핀 패드가 오른쪽에 있을 때
  위에서 아래 방향으로 **4(RX), 3(TX), 2(GND), 1(5V)** 이다. 배선은 명칭을
  기준으로 하며, 데이터선은 `LD2454 TX(3) → ESP32 RX`,
  `LD2454 RX(4) → ESP32 TX`로 교차한다.
- 정확한 핀 이름, UART 전압 허용 범위, 기본 baud rate는 모듈 라벨과 공식
  매뉴얼로 확인한다. 제조사 제품 안내에는 기본 UART가 256000 baud로 소개되어
  있다.
- ESP32의 USB 부트·로그에 쓰이는 UART0는 사용하지 않는다. 별도 하드웨어 UART와
  보드별 핀 맵을 `include/`의 추적기 전용 설정 인터페이스에 둔다.
- Wi-Fi 자격 증명, Pi 주소, 토큰, 방 보정값은 버전 관리되는 소스에 넣지 않는다.
  기존 `watchcat_config.example.h`와 같은 예제/로컬 설정 패턴을 따른다.

## 4. 데이터와 좌표계

### 4.1 원시 관측값

프레임마다 레이더가 보고하는 각 목표에서 아래처럼 정규화된 값을 만든다.
필드의 실제 단위와 부호는 공식 UART 문서의 예제 프레임으로 검증한다.

```json
{
  "observedAt": "2026-08-20T12:34:56.789Z",
  "sensorId": "living-room-radar-1",
  "sequence": 1842,
  "targets": [
    {
      "radarTargetId": 1,
      "xMm": -420,
      "yMm": 2150,
      "speedMmPerSec": 310,
      "distanceMm": 2191,
      "angleDeg": -11.1
    }
  ]
}
```

`radarTargetId`는 센서가 프레임 안에서 붙인 임시 번호다. 가려짐, 교차,
프레임 누락 뒤에 바뀔 수 있으므로 데이터베이스의 고양이 ID나 장기 이력의
주 키로 쓰지 않는다.

### 4.2 방 좌표 변환

레이더 기준 좌표를 웹 평면도 좌표로 바꾸기 위해 센서마다 다음 보정값을 둔다.

- `originXmm`, `originYmm`: 방 평면도에서 센서 안테나 중심의 위치
- `headingDeg`: 레이더 정면이 방의 +Y축과 이루는 각
- `mirrorX`: 설치 방향 때문에 좌우가 반전됐을 때의 보정
- `roomWidthMm`, `roomHeightMm`: 화면 축척과 구역 편집 기준

변환은 센서에서 하지 않고 Pi에서 한다. 설치를 다시 해도 펌웨어를 다시
올리지 않고 로컬 설정만 바꾸기 위해서다. 화면에는 원시 레이더 좌표와 보정된
방 좌표를 모두 진단용으로 표시할 수 있게 한다.

## 5. 추적·고양이 추정 정책

### 5.1 짧은 트랙 생성

Pi는 프레임 간 거리가 가까운 목표를 같은 `trackId`로 연결한다. 새로 들어온
목표가 최근 트랙의 마지막 위치에서 `TRACK_MATCH_DISTANCE_MM` 이내이고,
`TRACK_GAP_MS` 이내라면 같은 트랙으로 묶는다. 기본값은 현장 보정 전까지
각각 600 mm, 2,000 ms로 두며, 코드 상수 대신 로컬 설정으로 노출한다.

이 규칙은 레이더 ID의 변동을 완화할 뿐, 사람이 고양이로 바뀌어 보이는 상황을
완전히 해결하지 못한다. 따라서 트랙에는 다음 상태만 둔다.

| 상태 | 의미 |
|---|---|
| `new` | 첫 관측 또는 재획득 직후 |
| `active` | 최근 관측이 계속 들어옴 |
| `coasting` | 잠시 사라졌으나 마지막 위치를 짧게 유지 |
| `ended` | 시간 초과로 종료 |

### 5.2 고양이 여부

레이더만으로는 고양이 여부를 확정하지 않는다. UI와 이벤트에는 다음 세
수준을 사용한다.

| 판정 | 조건 | 화면 문구 |
|---|---|---|
| `motion` | 유효한 움직이는 목표 | 움직임 감지 |
| `catCandidate` | 고양이 전용 구역·속도·연속성 규칙을 만족 | 고양이 추정 |
| `catConfirmed` | 후보 발생 시 촬영된 이미지의 Hailo 결과가 cat | 고양이 확인 |

후보 판정은 초기에는 보수적으로 한다. 예를 들어 고양이 전용 통로에서 새
트랙이 0.5초 이상 계속되고, 무시 구역이 아니며, 촬영 쿨다운이 끝난 경우에만
카메라 촬영을 요청한다. 사람과 고양이가 함께 있는 집이라면 Hailo 확인 전의
푸시 알림·방문 통계는 `고양이 추정`으로만 표기한다.

### 5.3 중복 촬영 방지

- 같은 트랙 또는 같은 구역에는 `CAPTURE_COOLDOWN_MS` 동안 한 번만 촬영을
  요청한다.
- 이미 `capturePending` 또는 Hailo 추론이 진행 중이면 새 요청을 대기열에
  쌓지 않고, 마지막 레이더 이벤트 시각만 갱신한다.
- 카메라가 오프라인이거나 Hailo 오류이면 레이더 이력은 남기되 요청을
  반복하지 않는다.

## 6. 구역과 이벤트

구역은 방 좌표계 기준의 축 정렬 사각형으로 시작한다. 처음부터 복잡한 다각형
편집을 넣지 않는다.

```json
{
  "id": "food-bowl",
  "name": "밥그릇",
  "kind": "interest",
  "rect": { "xMm": 900, "yMm": 1800, "widthMm": 700, "heightMm": 600 },
  "captureOnEnter": true,
  "enabled": true
}
```

구역 종류는 다음 세 가지다.

- `interest`: 밥그릇·화장실·출입문처럼 방문을 기록하거나 촬영을 요청할 곳
- `ignore`: 커튼·선풍기·창가처럼 표시·이벤트·촬영에서 제외할 곳
- `context`: 소파·캣타워처럼 지도에는 보이되 알림을 만들지 않을 곳

이벤트는 `zone-enter`, `zone-exit`, `motion-start`, `motion-end`,
`capture-requested`, `cat-confirmed`로 기록한다. `zone-exit`는 관측이 사라진
즉시 만들지 않고 짧은 coasting 시간이 끝난 뒤에 만든다.

## 7. Pi API와 보관 설계

### 7.1 레이더 노드 수신 API

레이더 노드는 HTTPS 또는 신뢰할 수 있는 LAN의 HTTP로 아래 API에 관측 배치를
전송한다. 인증·토큰 처리 방식은 기존 카메라 API와 맞춘다.

`POST /api/v1/radar/observations`

- 인증: 기존 `Authorization: Bearer …` 방식
- 본문: `sensorId`, `observedAt`, `sequence`, `targets`
- 응답: `202 { "ok": true, "accepted": true }`
- 수신 검증: 센서 ID 허용 목록, 대상 수 상한(3), 숫자 범위, 미래 시각·너무
  오래된 시각, 요청 본문 크기를 검증한다.

전송 실패 시 ESP32는 최근 1–2개 배치까지만 RAM에 보관하고 이후 프레임은
버린다. 위치 데이터는 최신성이 중요하며, Wi-Fi 복구 뒤에 수분 전 궤적을
재전송하면 현재 화면을 오염시킨다.

### 7.2 상태 API

`GET /api/v1/radar/status`는 웹 UI와 TFT가 쓰는 요약 상태를 제공한다.

```json
{
  "ok": true,
  "sensorOnline": true,
  "lastObservedAt": "2026-08-20T12:34:56.789Z",
  "activeTracks": [
    { "trackId": "t-17", "xMm": 940, "yMm": 2040, "speedMmPerSec": 310,
      "classification": "catCandidate", "zoneId": "food-bowl" }
  ],
  "lastConfirmedCatAt": null,
  "lastError": null
}
```

`GET /api/v1/radar/history?from=…&to=…`는 시간 구간의 구역 이벤트와 축약된
궤적만 반환한다. 10 Hz 원시 프레임을 무기한 보관하지 않는다.

| 데이터 | 보관 정책 초안 |
|---|---|
| 실시간 관측 | 메모리의 최근 30초 링 버퍼 |
| 축약 궤적 | 1초 단위 또는 위치 변화가 클 때만 저장, 7일 |
| 구역·촬영·확인 이벤트 | 90일 |
| Hailo 확인 사진 | 기존 watchcat 사진 보관 정책을 따름 |

SQLite 파일 하나로 시작한다. 센서 설정과 이벤트의 쓰기량이 작고, 별도 서버를
추가하지 않아도 백업·점검이 쉽기 때문이다. 일별 활동 통계는 저장된 이벤트를
집계한다.

## 8. 웹 UI와 TFT 표시

### 8.1 Pi 웹 UI

기존 watchcat 웹 화면에 `레이더` 섹션 또는 별도 경로를 추가한다. 첫 UI는
WebSocket 없이 500–1,000 ms 폴링으로 시작한다. 레이더 자체가 약 10 Hz여도
브라우저를 10 Hz로 갱신할 필요는 없다.

화면 구성은 다음과 같다.

```text
┌─ 방 평면도 ────────────────────────────────────────────────┐
│ [무시: 창가]                         [컨텍스트: 캣타워]    │
│                                                           │
│             · · · ·  ● 고양이 추정                       │
│                      2.2 m / 0.31 m/s                    │
│                                                           │
│ [관심: 밥그릇]                    [관심: 화장실]          │
└───────────────────────────────────────────────────────────┘
레이더 온라인 · 마지막 프레임 0.2초 전 · 활성 트랙 1개
오늘: 밥그릇 6회 · 화장실 3회 · 확인된 고양이 12회
```

- 방 윤곽, 센서 위치·정면, 구역, 활성 트랙, 최근 10초 궤적을 같은 좌표계에
  표시한다.
- 트랙은 `움직임 감지`(회색), `고양이 추정`(노랑), `고양이 확인`(초록)으로
  구분한다. 색만으로 의미를 전달하지 않고 아이콘·문구도 함께 쓴다.
- 사용자는 구역을 추가·이동·활성화하고, 무시 구역을 만들 수 있다. 설정 저장은
  명시적 저장 버튼으로만 수행한다.
- 진단 패널에는 마지막 UART 프레임 시각, 수신 지연, 원시 목표 수, 마지막
  오류, 보정값을 표시한다.
- 고양이 확인 이벤트에는 Hailo가 판정한 최근 사진으로 이동하는 링크를 둔다.

### 8.2 캣모니터 TFT

240×280 TFT에는 지도 전체 대신 요약만 보여준다.

- 상단: `RADAR OK` / `RADAR OFFLINE` / `RADAR ERROR`
- 중앙: `고양이 확인`, `고양이 추정`, `움직임 없음` 중 하나
- 하단: 현재/마지막 구역명, 마지막 감지 후 경과 시간, 활성 목표 수
- 상세 버튼: 거리, 속도, 센서 신호 시각, 카메라/Hailo 확인 상태

카메라와 레이더의 값이 충돌하면 Hailo의 최근 이미지 판정을 “확인”으로,
레이더는 “현재 움직임”으로 따로 표시한다. 예: `현재 움직임: 밥그릇 / 최근
확인: 고양이 (12초 전)`.

## 9. 보정과 현장 검증

1. 레이더를 임시 고정하고 방 평면도를 실제 치수로 입력한다.
2. 바닥에 1 m 간격 표식을 붙이고 사람이 각 표식을 천천히 지나가며 x/y의
   좌우·전후 방향과 거리 단위를 확인한다.
3. 화면에서 센서 정면·원점·좌우 반전을 맞춘다.
4. 커튼, 선풍기, 창가, 문을 각각 5분씩 관찰해 반복 오탐 영역을 `ignore`로
   등록한다.
5. 고양이가 평소처럼 다니는 시간을 최소 하루 기록하고, 레이더 이벤트와
   카메라 사진을 비교한다.
6. 그 뒤에만 관심 구역 촬영, 쿨다운, `catCandidate` 규칙을 켠다.

완료 판정은 좌표가 “그럴듯해 보이는 것”이 아니라 다음 측정으로 한다.

| 항목 | 초기 성공 기준 |
|---|---|
| 좌표 방향 | 표식 5곳에서 좌우·전후가 화면과 일치 |
| 구역 진입 | 관심 구역 20회 중 18회 이상 올바른 구역 이벤트 |
| 고정 물체 오탐 | 무시 구역 등록 후 30분에 2회 이하 |
| 촬영 중복 | 같은 한 번의 통과에 촬영 요청 1회 이하 |
| 네트워크 복구 | Wi-Fi 복구 후 30초 이내 최신 관측 재개 |

## 10. 구현 순서와 파일 소유

### Phase R0 — UART 관측 도구

- 새 레이더 노드의 전원·UART 연결을 검증한다.
- 원시 바이트를 사람이 읽을 수 있는 로그로만 출력하고, 매뉴얼 예제와
  프레임 경계·부호·단위를 대조한다.
- 이 단계에서는 Pi 전송·카메라 촬영·설정 명령을 넣지 않는다.

### Phase R1 — 레이더 노드와 수신 API

- 레이더 노드에 프레임 파서, 유효성 검사, Wi-Fi 재연결, 최신 관측 전송을
  구현한다.
- Pi에 관측 수신 API와 메모리 링 버퍼를 구현한다.
- 카메라 노드와 Hailo 코드는 수정하지 않는다.

### Phase R2 — 지도·구역·이력

- Pi에서 방 좌표 변환, 트랙, 구역 이벤트, SQLite 보관을 구현한다.
- 웹 UI에 평면도와 진단 패널, 구역 편집을 추가한다.
- TFT에는 읽기 전용 요약 상태를 추가한다.

### Phase R3 — 카메라 확인 연동

- 관심 구역의 후보 이벤트를 기존 `POST /api/v1/capture` 명령과 연결한다.
- Hailo 결과를 해당 레이더 이벤트·트랙과 시간 기준으로 연계한다.
- 사람·고양이가 함께 있는 실제 환경에서 오탐·미탐·중복 촬영을 측정한다.

예상 파일 분리는 아래처럼 유지한다. 실제 파일명과 보드 선택은 R0에서 확정한다.

| 영역 | 예정 위치 | 비고 |
|---|---|---|
| 레이더 펌웨어 | `src/radar_node/`, `include/` | 카메라 노드와 별도 build filter |
| 레이더 로컬 설정 예제 | `include/*radar*_config.example.h` | 실값·토큰은 git 제외 |
| 레이더 서버 모듈 | `gateway/`의 별도 모듈 | 이미지 업로드 상태와 분리 |
| 영속 데이터 | Pi의 watchcat 데이터 경로 | SQLite와 백업 절차 문서화 |
| 설치·보정 | `docs/` | 이 문서와 현장별 설정 기록 |

## 12. 리스크와 완화

| 위험 | 영향 | 완화 |
|---|---|---|
| 레이더 ID 변동·사람과의 교차 | 잘못된 개체 추적 | ID 고정 금지, 짧은 거리 기반 트랙, Hailo 확인 |
| 정지한 고양이 미감지 | 재실 상태가 일찍 끝남 | `움직임`과 `고양이 확인`을 분리 표시, 카메라 결과 보존 |
| 커튼·선풍기 오탐 | 불필요한 촬영·통계 왜곡 | 현장 관측 뒤 ignore 구역, 촬영 쿨다운 |
| 미확인 UART 형식·펌웨어 차이 | 파서 오류 또는 설정 실패 | R0에서 수신 전용 검증, 매뉴얼 확인 전 설정 명령 금지 |
| Wi-Fi 단절 | 오래된 궤적 표시 | 최신 배치만 전송, 오프라인 상태·수신 시각 표시 |
| 기존 카메라/Hailo 경로 영향 | 기존 기능 회귀 | 별도 노드·모듈·상태, 단계별 통합 테스트 |

## 13. 프로젝트 규칙 확인

`AGENTS.md`와 `.codex` 프로젝트 설정을 확인했다. 보드별 핀 매핑과 Wi-Fi
자격 증명은 소스 제어에 넣지 않고, 카메라 캡처·네트워크·애플리케이션 동작을
분리한다. 카메라 프레임 버퍼, PSRAM, task stack, watchdog은 고위험 영역이므로
레이더 노드를 카메라 노드에 병합하지 않는 방향을 기본으로 한다.
